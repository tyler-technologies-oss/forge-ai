The AI Chatbot Launcher provides a page-embedded chat experience featuring a centered welcome/hero view that transitions into a full conversation interface when the user sends their first message. It combines a visually engaging landing state with full chatbot functionality.

## Features

- **Welcome view**: Centered hero layout with customizable icon, title, description, and suggestions
- **Conversation view**: Full chat interface with header controls (clear, export, agent selection)
- **History view**: Full-height chat history browser with search, infinite scroll, and a keyboard-accessible "Load more" action, reached via the prompt bar's history button
- **Animated transitions**: Smooth state changes between welcome, conversation, and history modes
- **Artifact canvas**: A panel beside the conversation for tool output or app-provided content, with the thread narrowing to a sidebar-style column

## When to Use

Use the AI Chatbot Launcher when you want:

- A dedicated landing page or section for AI chat
- A visually appealing entry point before conversation begins
- Multi-agent support with header-based agent switching
- Built-in welcome-to-conversation state management

For inline embedded experiences without a welcome view, consider `<forge-ai-chatbot>`. For floating/overlay patterns, use `<forge-ai-floating-chat>`.

## Usage Patterns

### Welcome Mode (Default)

Initial state displays a centered hero with icon, title, description, and optional suggestions. The prompt input is prominent and wrapped in a gradient container.

### Conversation Mode

After sending the first message, transitions to a full chat interface with:

- Header showing title, agent selector, and action buttons
- Scrollable message thread
- Bottom-anchored prompt area

### Chat History

Set `showHistoryButton` to put a history button in the prompt bar's bottom-left, and `threads` (plus optionally `totalThreads`/`threadsLoading`) to populate it. Clicking it opens a "Chat history" popover with a preview of recent chats; a search field appears once there are more than 5 chats. "View all" transitions into a full-height history view (a new `history` state alongside `welcome`/`conversation`) built on `<forge-ai-threads-search>`, with a back button returning to the conversation (if one exists) or welcome view.

Visibility is yours to decide, matching `showConversationsButton` on `<forge-ai-chatbot>` — the component never infers it from whether chats are loaded. An empty `threads` shows "No chats yet" in the popover rather than removing the entry point, so a user with no history still sees where their history will live.

Search and pagination are backed by `forge-ai-chatbot-launcher-thread-search` and `forge-ai-chatbot-launcher-thread-load-more` (same shape in both the popover and the full view), thread selection by `forge-ai-chatbot-launcher-thread-select`, and rename/delete reuse the existing `forge-ai-chatbot-launcher-thread-rename`/`-thread-delete` events. See the `WithHistory` story below for a full mock-backend wiring example.

### Owning Thread Selection

`forge-ai-chatbot-launcher-thread-select` is cancelable. By default the component commits the selection itself — it sets `selectedThreadId` and moves to the conversation view as soon as the thread is clicked. That is fine when a thread is always available locally, but if you load threads from a server the load can fail, and the component will already be showing a thread it never opened.

Call `preventDefault()` to take ownership of both commitments. The component then changes nothing, and you commit once your load resolves:

```ts
launcher.addEventListener('forge-ai-chatbot-launcher-thread-select', async evt => {
  evt.preventDefault();
  launcher.threadsError = undefined;
  launcher.threadsLoading = true;

  try {
    const messages = await api.loadThread(evt.detail.id);
    launcher.selectedThreadId = evt.detail.id;
    // setThreadState transitions to the conversation view on its own once it has messages.
    await launcher.setThreadState({ threadId: evt.detail.id, messages }, { skipAnimation: true });
  } catch (error) {
    // Nothing to undo - selectedThreadId and the view state were never touched.
    launcher.threadsError = error.message || 'Could not open that chat.';
  } finally {
    launcher.threadsLoading = false;
  }
});
```

Do **not** call `startConversation()` before the load. Transitioning up front means a failed load has to walk the user back to the welcome view, which reads as a flicker. Let `setThreadState()` perform the transition when it succeeds, and surface the failure in place — the history button's error badge and the popover's retry are already wired to `threadsError`.

### Handling a Failed History Load

An empty `threads` array on its own reads as "no chats yet", so a failed load would otherwise be indistinguishable from a user with no history. Set `threadsError` to a message: the history button picks up an error badge so the failure is visible with the popover closed, and the popover and full history view show the message with a **Retry** button in place of the empty state.

If chats are already loaded the list stays visible, and the message renders as a compact single line with a **Retry** instead of the banner. Where it sits depends on what failed: a failure that arrives while a page is in flight is a pagination failure, so it reads at the bottom of the list where the load-more spinner would have appeared. Any other failure — a rejected thread selection, for instance — is not tied to the end of the list, so it sits above it.

Retry dispatches `forge-ai-chatbot-launcher-thread-retry`. It is a plain notification — re-request the chats, and clear `threadsError` once the load succeeds. An error supersedes `threadsLoading`, so the two never render together.

```ts
launcher.threadsError = 'Could not load your chat history.';

launcher.addEventListener('forge-ai-chatbot-launcher-thread-retry', async () => {
  launcher.threadsError = undefined;
  launcher.threadsLoading = true;
  try {
    launcher.threads = await api.loadThreads();
  } catch (error) {
    launcher.threadsError = error.message || 'Could not load your chat history.';
  } finally {
    launcher.threadsLoading = false;
  }
});
```

Always fall back to your own copy rather than assigning `error.message` directly — an empty message reads as "no error" and hides the badge along with the retry.

### Moving Between Views

`viewState` is read-only; each view has a method that navigates to it. `startConversation()` and `showHistory()` move to the conversation and full history views, and `showWelcome()` returns to the welcome view. All three change only the view — use `startNewChat()` when the conversation itself should be reset, since it also clears messages, nulls `selectedThreadId`, and resets the adapter's thread.

### Artifact Canvas

The canvas is a panel that opens to the right of the conversation for content that deserves more room than a message: a large table, a document, a chart, or later an MCP App. When it opens, the conversation animates into a sidebar-style column (`--forge-ai-chatbot-launcher-chat-width`, 420px by default) and the canvas takes the remaining width. It is only available in the conversation view; leaving that view closes it.

There are three ways to put content in the canvas.

**From your app.** Call `openCanvas()` while in the conversation view. Without `content` the `canvas` slot is shown; pass a `Node` as `content` to mount something built on the fly. `title` overrides `canvasTitle` for that content, and `canvas-actions` adds buttons to the canvas header. `closeCanvas()` and the `canvasOpen` getter round out the API. Both open and close dispatch cancelable events (`forge-ai-chatbot-launcher-canvas-open` / `-canvas-close`); a close forced by leaving the conversation view is not cancelable.

```ts
launcher.openCanvas({ title: 'Release notes' }); // shows the `canvas` slot
launcher.openCanvas({ title: 'Report', content: buildReportElement() });
launcher.closeCanvas();
```

<Canvas of={AiChatbotLauncherStories.WithCanvas} />

**From a tool definition.** Add a `canvas` block to a tool that already has a `renderer`. With `open: 'on-request'` (the default) the tool renders inline as usual, and its renderer is told a canvas is available via `presentation = 'inline-expandable'` so it can show an expand affordance. The bundled data table does this.

<Canvas of={AiChatbotLauncherStories.CanvasOnRequest} />

With `open: 'auto'` the canvas opens as soon as the tool call renders, and the thread shows a compact `<forge-ai-artifact-card>` in place of the renderer so the artifact can be reopened, or collapsed, from the thread. The card's `title`, `subtitle`, `icon`, and `actionLabel` come from the `canvas` block, each a static value or a function of the typed tool call, so the agent supplies them through whatever `args` you expose (or your handler's `result`). `title` also names the canvas. The mapping is documented in full under [Getting Started → Client-Side Tools](?path=/docs/getting-started-client-side-tools--docs).

```ts
const tool: ToolDefinition<DataTableArgs> = {
  ...displayDataTableTool,
  canvas: {
    open: 'auto',
    title: toolCall => toolCall.args.title ?? 'Data table',
    subtitle: toolCall => `${toolCall.args.rows.length} rows`,
    actionLabel: { open: 'Open table in canvas', collapse: 'Collapse table' }
  }
};
```

<Canvas of={AiChatbotLauncherStories.CanvasAutoOpen} />

`inline` controls what the thread shows independently of when the canvas opens: `renderer` (default for `on-request`), `card` (default for `auto`), or `card-while-open`. Combining `card` with the default `on-request` puts the card in the thread first and opens the canvas only when the user clicks it, which suits large artifacts that should not open unprompted.

<Canvas of={AiChatbotLauncherStories.CanvasCard} />

`card-while-open` keeps the renderer inline and swaps it for the card only while that tool call is the one in the canvas. The card is marked `active` for the duration, clicking it again collapses the canvas, and the renderer returns when the canvas closes. This is the opt-in for any tool whose inline output would just duplicate the canvas.

```ts
const tool: ToolDefinition = {
  ...displayDataTableTool,
  canvas: { ...displayDataTableTool.canvas, inline: 'card-while-open' }
};
```

<Canvas of={AiChatbotLauncherStories.CanvasCardWhileOpen} />

**From a renderer component.** Any tool renderer can ask for the canvas by calling `requestCanvasOpen(this, { toolCallId, toolName, title })` from `@tylertech/forge-ai`. The launcher creates a fresh instance of the tool's renderer (or `canvas.renderer` when provided) with `presentation = 'canvas'`. Hosts without a canvas leave the request unhandled, so renderers should only show the affordance when `presentation` is `inline-expandable`.
